# Панель администратора

Путь: /admin. Ссылка появляется в личном профиле после входа администратора. Обычный пользователь получает 403 от admin API независимо от видимости ссылок; анонимный — 401.

## Функции

- Поиск пользователей по email, список с пагинацией (20 по умолчанию, максимум 100).
- Карточка: email, роль, статус, профиль и число активных сессий.
- Блокировка / разблокировка с обязательной причиной.
- При блокировке все сессии отзываются, повторный вход запрещается. После разблокировки нужен новый вход: старые сессии не восстанавливаются.
- Журнал: исполнитель, пользователь, действие, причина и время. Пароли, хеши и токены в admin API не выдаются.
- Суперадминистратор назначает и снимает администраторов в карточке пользователя, указывая причину. Все сеансы при изменении роли отзываются; нужен новый вход.
- Обычный администратор имеет те же возможности просмотра и модерации, но не управляет ролями. Можно блокировать обычных администраторов; себя и суперадминистратора блокировать нельзя.
- Суперадминистратора нельзя понизить через API. Его статус хранится в БД, не определяется email. Ограничение БД запрещает сочетание этой роли с блокировкой или is_admin=false.
- Заблокированного пользователя сначала нужно разблокировать, затем назначать администратором. Удаления аккаунтов нет.

## Назначение первого администратора / суперадминистратора

Миграция 0003 создаёт is_admin=false и is_blocked=false для всех существующих пользователей. Миграция 0004 добавляет is_super_admin=false для всех; существующие администраторы автоматически не повышаются. Нет публичного bootstrap endpoint и правила «первый зарегистрированный становится админом».

Сначала владелец проекта явно выбирает уже зарегистрированный аккаунт приложения. Затем оператор с доступом к серверному DATABASE_URL выполняет из backend:

```sh
.venv/bin/python -m app.manage_admin --email chosen-account@example.com
# Только по явному выбору владельца проекта:
.venv/bin/python -m app.manage_admin --email chosen-owner@example.com --super-admin
```

Это пример адреса, не настоящий администратор. Не запускать команду для произвольного email и не передавать DATABASE_URL в командной строке или чат. Использовать уже настроенное серверное окружение. Команда не создаёт пользователя, не повышает заблокированный аккаунт и записывает operator_grant_admin / operator_grant_super_admin в журнал. При повышении существующие сессии отзываются; после назначения нужно войти заново.

На Render Free shell может быть недоступен; назначение можно провести доверенным оператором через защищённое подключение к Neon после явного выбора аккаунта владельцем. Новое право не должно автоматически выдаваться email из переменной окружения: email в текущей версии ещё не верифицируется.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/admin/users?q=...&offset=0&limit=20 | Список и поиск |
| GET | /api/admin/users/{id} | Карточка пользователя |
| PATCH | /api/admin/users/{id}/block | blocked: true/false, reason: строка 3–500 символов |
| PATCH | /api/admin/users/{id}/role | Только superadmin: is_admin: true/false, reason: строка 3–500 символов |
| GET | /api/admin/events?limit=50 | Последние события, максимум 100 |

Все ответы admin API используют Cache-Control: no-store. Изменения защищены общей проверкой Origin. Роль и блокировка проверяются по БД при каждом запросе. Изменения блокировки/роли блокируют строки исполнителя и цели в стабильном порядке и повторно проверяют актуальные права. Вход использует тот же row-lock пользователя. Изменение статуса и событие аудита сохраняются одной транзакцией.

## Проверки

PostgreSQL-тесты: запрет доступа анонимному и обычному пользователю; отсутствие повышения через register/profile; bootstrap выбранного аккаунта и отзыв старых сессий; безопасный список; поиск с буквальным %; карточка; защита самого себя и суперадминистратора; причина блокировки; отзыв сессий; запрет входа блокированному; разблокировка и новый вход; журнал. Frontend-тесты: отсутствие запроса списка без прав, вход, просмотр и блокировка с причиной.

## Границы версии

Нет удаления пользователей, смены чужого пароля и назначения суперадминистраторов через веб. Это отдельные операции с дополнительной проверкой прав и подтверждением. Журнал защищён правами приложения; он не является внешним неизменяемым аудитом.

Делегирование проверено интеграционными тестами: только superadmin меняет роли; нельзя повыситься через register/profile/role; владелец защищён; заблокированный пользователь не повышается; при назначении и снятии роли старые сеансы теряют доступ; журнал не дублируется при повторном запросе. Frontend проверяет назначение/снятие роли, обязательную причину и скрытие операций без прав.
