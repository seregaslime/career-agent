# План создания проекта

Оценка: 8–10 учебных недель при 10–15 часах работы ведущего в неделю и регулярных небольших вкладах остальных. Это ориентир, не обещание срока. Каждый этап завершается проверяемым результатом; следующий начинаем после приёмки предыдущего. Если работа почти полностью ложится на одного человека, уменьшаем объём или переносим срок.

## Критический путь

Каркас → БД и вход → профиль и интервью → резюме; затем интеграция с подбором → обучение → сквозная приёмка. Данные рынка можно готовить параллельно. Если реальный API не доступен, не блокируем MVP: используем явно обозначенный demo-набор.

## Правила одной задачи

Задача содержит цель, входные данные, результат и критерий готовности. Берём не больше одной крупной задачи на человека. API и JSON-примеры согласуем до параллельной работы. Интегрируем небольшими PR минимум раз в неделю. Definition of Done: результат работает, ошибки обработаны, значимые проверки пройдены, инструкция обновлена, секретов и личных данных в diff нет.

## Контрольные демонстрации

1. Конец этапа 2: вход и сохранение профиля.
2. Конец этапа 4: интервью и скачанный PDF.
3. Конец этапа 7: весь пользовательский путь на demo-данных.
4. Конец этапа 9: финальный показ с резервным offline/demo-сценарием.

## Риски и действия

| Риск | Что делаем |
|---|---|
| Основная нагрузка на ведущего | Отдаём ограниченные независимые задачи; откладываем функции после MVP |
| LLM добавляет неподтверждённый опыт | Структурированные факты, подтверждение пользователем, проверка перед резюме |
| API вакансий недоступен | Адаптер источника и синтетический набор; проверка условий API до интеграции |
| Слишком сложная архитектура | Модульный монолит и одна БД; новые компоненты после измерений |
| Качество matching непонятно | Фиксированный набор профилей и ручная оценка объяснений |
| Срыв перед защитой | Рабочая демонстрация после каждого этапа, последние недели — резерв |

## Ближайший шаг: этап 2 — данные и вход

1. Зафиксировать модель User, Session и Profile и контракт API.
2. Добавить миграции пользовательских таблиц.
3. Реализовать регистрацию, вход, выход и текущего пользователя.
4. Сделать чтение и редактирование своего профиля.
5. Добавить формы входа и профиля в frontend.
6. Проверить тестами, что один пользователь не получает доступ к данным другого, а профиль сохраняется после повторного входа.
7. Провести ревью, PR, CI и проверить обновление облачного стенда.

Критерий завершения: пользователь регистрируется, входит, сохраняет профиль, выходит и после повторного входа видит свои данные. После этого переходим к интервью с агентом (этап 3).
